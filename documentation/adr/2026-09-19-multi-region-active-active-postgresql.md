# ADR-2026-09-19: Multi-Region Active-Active PostgreSQL (Logical Multi-Master Replication)

## Status

**Proposed** | Accepted | Rejected | Superseded | Deprecated

## Context

GitHub issue #1187 requests support for true multi-region active-active deployments: one KMS
instance group and one local PostgreSQL node per region, each serving reads/writes locally for
low latency, converging state across regions via a Postgres logical-replication multi-master
extension (Spock/pgEdge, EDB Postgres Distributed, Postgres-BDR, or a hand-rolled pglogical
setup). The KMS today only supports single-writer PostgreSQL topologies (primary + optional hot
standbys via `target_session_attrs=read-write`).

Several concrete gaps make this unsafe today:

- **`tags` and `read_access`** are declared with only `UNIQUE (id, tag)` / `UNIQUE (id, userid)`
  on **nullable** columns. This is not a valid `REPLICA IDENTITY` for logical replication —
  Postgres refuses to replicate `UPDATE`/`DELETE` statements on a table with no usable identity.
  **`crypto_officer_activations`** has no key at all in PostgreSQL/SQLite (only MySQL already has
  a surrogate `id` PK).
- **RFC 5280 §5.2.3** requires CRL Number extensions to be strictly monotonically increasing
  per issuer. Uncoordinated concurrent CRL generation from two regions cannot satisfy this.
- **Crypto Officer ceremony activation/revocation** is quorum-sensitive; correctness matters
  more than availability, so uncoordinated concurrent activation from two regions is unsafe.
- **KMIP object `State`** transitions are currently blind overwrites
  (`UPDATE objects SET state = $1 WHERE id = $2`) in every backend. Verified: Spock's own
  default conflict resolution (`spock.conflict_resolution = 'last_update_wins'`, confirmed in
  pgEdge's reference `docker-compose.yaml`) is commit-timestamp based, not rank based — it does
  **not** implement `GREATEST(state)` semantics. A later-committing `Deactivated` write can
  silently overwrite an earlier-committing `Destroyed`/`Compromised` write once replicated,
  undoing a security-critical state.
- A genuine, legitimate **local** backward `State` transition already exists:
  `message.rs::revert_activation_to_preactive` reverts `Active`/`PreActive` objects back to
  `PreActive` as part of KMIP batch UNDO. Any conflict-resolution mechanism must not interfere
  with this existing local behavior.
- **Grants/permissions** (`read_access`) can legitimately race (a concurrent grant + revoke on
  the same object/user): a full CRDT/OR-Set merge is a substantial undertaking explicitly
  deferred by the issue.

## Decision

Implement multi-region active-active support generically — no code path specific to pgEdge or
any other named extension — validated end-to-end against `ghcr.io/pgedge/pgedge-postgres`
(pgEdge Community, free and open-source, the issue's named reference implementation).

### 1. PostgreSQL-only schema hardening (real PRIMARY KEYs)

`tags` and `read_access` gain a real composite `PRIMARY KEY` on their existing key columns
(`ALTER COLUMN ... SET NOT NULL` + `CREATE UNIQUE INDEX CONCURRENTLY` + `ADD CONSTRAINT ...
PRIMARY KEY USING INDEX`, non-blocking). `crypto_officer_activations` gains a new
`id BIGINT GENERATED BY DEFAULT AS IDENTITY` surrogate `PRIMARY KEY`, matching MySQL's existing
shape. PostgreSQL automatically adopts the new PK as `REPLICA IDENTITY DEFAULT`. Rolled out
idempotently and automatically at server startup inside `PgPool::instantiate` — no manual
operator migration. SQLite and MySQL are unaffected (SQLite is never a multi-master target;
MySQL already has real PKs on all three tables).

### 2. Object `State` conflict merge via an `ENABLE ALWAYS` trigger with explicit undo bypass

A single PostgreSQL `BEFORE UPDATE FOR EACH ROW` trigger on `objects`, marked
`ALTER TABLE objects ENABLE ALWAYS TRIGGER ...`, coerces any state update to
`GREATEST(local_state, incoming_state)` using the KMIP `State` lifecycle ranking
(`PreActive=1 … Destroyed_Compromised=6`, SP800-57-1) whenever it would downgrade the row.
`ENABLE ALWAYS` ensures the monotonic guard protects against cross-region write races in all
scenarios: both when a lower-rank state arrives via replication, and when a local write
(e.g. `Deactivated`) races against a state that was already replicated in at a higher rank
(e.g. `Destroyed`).

To preserve the legitimate backward transition required by KMIP batch UNDO
(`revert_activation_to_preactive`), the trigger checks `current_setting('kms.allow_backward_state_transition', true)`.
When set to `'on'`, the guard is bypassed. A dedicated trait method
`ObjectsStore::update_state_allow_downgrade` (implemented on `PgPool` via `SET LOCAL kms.allow_backward_state_transition = 'on'`)
is called exclusively by `revert_activation_to_preactive`, scoping the bypass strictly to
the batch-UNDO revert path.

### 3. Static `region_role` server setting

A single new global, non-interactive setting `region_role: RegionRole` (`leader` | `follower`,
CLI `--region-role`, env `KMS_REGION_ROLE`, default `leader`). No election or consensus — it
only changes when an operator changes topology. Follows the existing flat top-level field
convention (`default_username`, `kms_public_url`); no configuration wizard prompt (matching the
precedent of every other simple non-interactive setting, e.g. `AuditFailureMode`).

### 4. Leader-only gating for exactly two operations

A single shared `crate::core::require_leader_region(kms, action)` helper rejects, with
`KmsError::InvalidRequest` (HTTP 422, reusing the existing "operation not permitted in this
configuration" error pattern), any call on a `follower` node to:

- CRL generation/regeneration (`generate_crl()` — the single entry point shared by the REST
  endpoint, the post-`Revoke` auto-trigger, and the background cron refresh).
- Crypto Officer ceremony activation (`perform_crypto_officer_ceremony_activation`) and
  revocation (`disable_crypto_officer_ceremony`).

Every other KMIP/REST operation (object CRUD, Locate, Grant/Revoke access, etc.) is unaffected
and continues to work locally in every region.

### 5. Crypto Officer ceremony state replicates like any other row

`crypto_officer_activations` is an ordinary table in the `public` schema replication set (added
via `spock.repset_add_all_tables('default', ARRAY['public'])`), so the `INSERT`/`UPDATE` rows
written by `perform_crypto_officer_ceremony_activation()`, `disable_crypto_officer_ceremony()`,
and `revoke_crypto_officer_activation()` — all three gated to the leader region via
`require_leader_region` — replicate normally to every follower. Because only the leader ever
writes this table, it is effectively single-writer even in the active-active topology: no
conflict-resolution trigger analogous to the `objects.state` guard is needed.

Consequence: once a Crypto Officer ceremony completes on the leader, that user is recognized as
an active Crypto Officer on every follower region too, as soon as the row replicates — there is
no separate per-region CO status. This is eventually consistent (ordinary replication lag), not
synchronous.

**Precondition**: every region's KMS server MUST be configured with the identical
`ceremony_secret` (or a `ceremony_key_id` resolving to the same underlying AES-256 key
material) — `Database::is_crypto_officer_activated_by` AES-256-GCM-decrypts the replicated
`sealed_record` using the **local** node's derived `CeremonyKeys`
(`crate/server_database/src/ceremony_keys.rs`); a mismatched key produces a GCM verification
failure.

Validating this surfaced a related fail-secure gap, now fixed:
`Database::verify_ceremony_record` (`crate/server_database/src/core/database_permissions.rs`)
previously propagated that verification failure as a hard `Err` (`DbError::CryptographicError`).
Unlike `dispatch.rs::check_role_permission`'s existing graceful fallback for the identical
condition, this was not caught by `KMS::is_crypto_officer()` or the
`/access/crypto_officer/status` active-CO-list loop, so either path would hard-fail (500-class
error) instead of treating the record as not-currently-active. `verify_ceremony_record` now
catches `DbError::CryptographicError` specifically and returns `Ok(false)` with a warning log —
consistent with the "tampered records fail unsealing" security invariant already documented on
`CeremonyKeys::unseal`.

### 6. Grants/permissions: accepted last-write-wins (no code change)

Concurrent conflicting writes to `read_access` converge via Spock's own default row-level
conflict resolution (`last_update_wins`). A concurrent grant + revoke on the same object/user can
silently drop one side. This is an accepted, documented v1 limitation; an operation-level
OR-Set/CRDT merge is out of scope here and tracked as separate future work.

### 7. Validation

A live 2-node CI integration test (`ghcr.io/pgedge/pgedge-postgres:16-spock5-standard`, wired
with real `spock.node_create`/`spock.sub_create` full-mesh subscriptions) proves convergent
behavior for concurrent `State` writes in both commit orderings and for a concurrent grant/revoke
race, alongside a faster single-node unit test that exercises the trigger directly.

## Consequences

### Positive

- **POS-001**: Multi-region active-active PostgreSQL works with any Spock/BDR/pglogical-class
  logical multi-master extension — no vendor lock-in to pgEdge specifically.
- **POS-002**: Minimal behavior change on single-writer PostgreSQL deployments: normal forward
  state transitions operate identically, and batch UNDO utilizes the scoped bypass.
- **POS-003**: The `State` conflict merge is enforced inside PostgreSQL under `ENABLE ALWAYS`,
  preventing both replicated downgrades and local overwrite races against already-replicated
  higher-rank states.
- **POS-004**: The existing local KMIP batch-UNDO backward `State` transition
  (`revert_activation_to_preactive`) is preserved via the explicit, transaction-local
  `kms.allow_backward_state_transition` bypass in `update_state_allow_downgrade`.
- **POS-005**: Real PRIMARY KEYs on `tags`/`read_access`/`crypto_officer_activations` are a
  strict correctness improvement independent of multi-region use (valid `REPLICA IDENTITY` is
  also a prerequisite for other logical-replication use cases, e.g. read replicas via
  `pg_logical`/CDC tooling).
- **POS-006**: Crypto Officer ceremony activation converges to every region automatically via
  the standard `public`-schema replication set — no additional trigger or leader-only read gate
  is needed, since only the leader ever writes `crypto_officer_activations`.

### Negative

- **NEG-001**: Grants/permissions accept a known, documented last-write-wins race (a concurrent
  grant + revoke on the same object/user can silently drop one side). No OR-Set/CRDT merge is
  implemented in this iteration.
- **NEG-002**: `region_role` is a static, operator-set value with no election or consensus; a
  misconfigured deployment with two `leader` regions (or zero) is not detected or prevented by
  the KMS itself.
- **NEG-003**: Leader gating is global per deployment (one leader for every issuer/CO ceremony),
  not per-issuer; a deployment with independent CAs cannot assign different leader regions to
  different CAs in this iteration.
- **NEG-004**: A rejected follower request is a hard error, not a transparent proxy to the
  leader; clients must know to retry against the leader region themselves.
- **NEG-005**: CO activation/revocation recognition on a follower lags by ordinary replication
  latency — there is a short window after a leader-side ceremony completes (or is revoked)
  during which a follower still reports the pre-change status.
- **NEG-006**: Operators MUST keep `ceremony_secret`/`ceremony_key_id` identical across every
  region. If they diverge, every follower fails to verify replicated ceremony records (fails
  secure to "not CO", per IMP-007) and CO ceremonies effectively stop working on that region
  until the secret is corrected.

## Alternatives Considered

### Rank comparison enforced in Rust (`update_state`) instead of a database trigger

- **ALT-001 Description**: Derive `Ord`/`PartialOrd` on the KMIP `State` enum and enforce
  monotonicity inside each backend's `update_state`/`atomic` implementation.
- **ALT-002 Rejection Reason**: Cannot intercept a row applied directly by the replication
  extension's apply worker, which writes to the table via its own internal mechanism, entirely
  bypassing the KMS's `ObjectsStore` trait layer. The merge must live inside the database.

### `ENABLE REPLICA` trigger without local write protection

- **ALT-003 Description**: Mark the monotonic-guard trigger `ENABLE REPLICA` so it fires only
  for incoming replication apply workers (`session_replication_role = 'replica'`).
- **ALT-004 Rejection Reason**: While `ENABLE REPLICA` would avoid needing any bypass for local
  batch UNDO, empirical testing on a live 2-node cluster proved it leaves a critical gap: if a
  higher-rank state (e.g. `Destroyed`) has already replicated into node B, a subsequent local
  write on node B (e.g. `Deactivated`) executes under `session_replication_role = 'origin'`,
  bypassing the replica-only trigger and silently overwriting `Destroyed` back down to `Deactivated`.
  Using `ENABLE ALWAYS` combined with a scoped `SET LOCAL` bypass for batch UNDO is required
  for end-to-end convergence.

### Dynamic leader election / consensus (Raft, etcd, Patroni-style)

- **ALT-005 Description**: Automatically elect a leader region and fail over on leader loss.
- **ALT-006 Rejection Reason**: Explicitly out of scope per the issue; adds a new consensus
  dependency and failure domain the issue does not ask for. A static, operator-set value is
  sufficient since regional topology changes are rare, deliberate operator actions.

### Transparent cross-region proxying of leader-only requests

- **ALT-007 Description**: A follower receiving a CRL/ceremony request forwards it to the
  leader region and relays the response.
- **ALT-008 Rejection Reason**: Adds a new synchronous cross-region dependency and leader
  discovery mechanism. A clear rejection error keeps every region's failure domain independent
  and is explicitly what the issue asks for ("no transparent proxying").

### Per-issuer leader granularity

- **ALT-009 Description**: Allow a different leader region per CA/issuer instead of one global
  leader for the whole deployment.
- **ALT-010 Rejection Reason**: Unnecessary complexity for the first iteration; explicitly
  deferred by the issue as future work.

## Implementation Notes

- **IMP-001**: All schema and trigger DDL lives in
  `crate/server_database/src/stores/sql/pgsql.rs::PgPool::instantiate`, gated idempotently via
  `pg_constraint` catalog lookups (same pattern as the existing `wrapping_key_id` backfill gate).
  `CREATE INDEX CONCURRENTLY` statements are each issued as their own single-statement
  `batch_execute` call (cannot run inside a transaction block).
- **IMP-002**: The trigger's rank `CASE` mapping mirrors the `State` enum's existing numeric
  discriminants (`crate/kmip/src/kmip_0/kmip_types.rs`) against the exact strings produced by its
  `Display`/`to_string()` implementation (verified: plain `strum::Display`, no
  `#[strum(serialize=...)]` override). `ENABLE ALWAYS` enforces rank monotonicity for all updates,
  with a `SET LOCAL kms.allow_backward_state_transition = 'on'` check allowing explicit downgrade
  in `update_state_allow_downgrade`.
- **IMP-003**: `region_role` flows `ClapConfig` → `ServerParams` exactly like every other simple
  global setting (`default_username`), with no wizard prompt and no client-side config mirroring.
- **IMP-004**: The `require_leader_region` gate lives in `crate/server/src/core/mod.rs` and is
  called from exactly three sites: `generate_crl()`,
  `perform_crypto_officer_ceremony_activation()`, and `disable_crypto_officer_ceremony()`.
- **IMP-005**: Validated against `ghcr.io/pgedge/pgedge-postgres:16-spock5-standard` via a new
  `mise run test:db:pgedge` 2-node CI task (`spock.node_create`/`spock.repset_add_all_tables`/
  `spock.sub_create`/`spock.sub_wait_for_sync` full-mesh wiring), plus a faster single-node
  `test_db_postgresql_state_monotonic_merge` unit test in the standard `psql` CI test type.
- **IMP-006**: Success criteria — `cargo clippy-all` and `cargo test -p
  cosmian_kms_server_database` pass; the new pgEdge CI test demonstrates convergent behavior for
  concurrent grant/revoke and concurrent state-transition scenarios in both commit orderings.
- **IMP-007**: `crypto_officer_activations` requires no monotonic-merge trigger (unlike
  `objects.state`) because writes are single-writer (leader-only).
  `Database::verify_ceremony_record` fails secure (`Ok(false)`, not `Err`) on a
  `DbError::CryptographicError` from `CeremonyKeys::unseal`, covering both genuine tampering and
  a cross-region `ceremony_secret`/`ceremony_key_id` mismatch.
