# 5.30.0 release notes (full text)

Full text of the `## [5.30.0]` entry of `CHANGELOG.md` as it was before it was condensed into a summary.

## [5.30.0] - 2026-11-28

### ⚠️ Breaking Changes

#### Vault API

- `vault_auth_verifier_url` now receives standard Vault paths: the KMS calls `GET <url>/v1/auth/token/lookup-self` and forwards `/v1/auth/*` requests unchanged (it used to call `/auth/token/lookup-self` and strip `/v1`). **Upgrade action:** point it at an OpenBao/Vault server, or at a Cosmian Auth Verifier that serves `/v1/auth/*`; upgrade an older Auth Verifier together with the KMS ([#863](https://github.com/Cosmian/kms/issues/863))

#### Database

- Objects wrapped by the server `key_encryption_key` are bound to their database row: the wrapped plaintext carries the vendor attribute `x-cosmian-stored-uid` and an object whose binding is missing or names another row is refused. At every start with a `key_encryption_key` the server wraps the existing objects again, bound to their row (SQLite, PostgreSQL, MySQL, Redis-with-Findex), so no manual migration is needed. **Upgrade action:** stop every 5.29.0 instance before starting 5.30.0, because rows written by 5.29.0 are refused until the next restart of 5.30.0. With an RSA-OAEP `key_encryption_key`, the bound plaintext must fit one RSA-OAEP block: a 2048-bit KEK limits the UID of a stored key to about 58 characters; AES KEKs are not concerned ([#1519](https://github.com/Cosmian/kms/issues/1519))

### 🔒 Security

- Bump the statically linked OpenSSL from 3.6.2 to 3.6.5 (CVE-2026-63073, CVE-2026-34182, CVE-2026-75803) and build the Docker image runtime (curl, wget, bash, glibc, CA bundle) from nixos-26.05 instead of nixos-24.11, which removes the fixable CVEs of curl 8.11.0, openssl 3.3.2, nghttp2 1.64.0 and zlib 1.3.1 (COSMIAN-2026-049, [#1349](https://github.com/Cosmian/kms/issues/1349))
- Stop a configured Operator role from administering PKCS#11: Operators lose `PKCS11`, `RNGSeed` and `SetConstraints` once roles are configured, and `PKCS11` and Set Constraints need a configured Crypto Officer; Operators keep every other operation on the objects they own or were granted. **Upgrade action:** add `[roles] crypto_officer_users` before calling Set Constraints (COSMIAN-2026-050)
- Stop writing KMIP payloads to debug logs: the KMIP request debug log (`cosmian_kms_server=debug`) reads an allowlist of fields from the raw request (protocol version, key identifier, algorithm, block cipher mode), and the `Display` of KMIP 2.1 operations and objects prints only `<N bytes>` for byte strings (data, IV, nonce, AAD, tags, signatures, MACs, PKCS#11 parameters, opaque and certificate values), so logging `{request}` cannot leak plaintext, ciphertext or PINs (COSMIAN-2026-051)
- Bound the work of KMIP requests: reject cyclic or oversized certificate chains, and resolve only the HSM keys granted to a user who is not an HSM administrator before a Locate, within the requested page, instead of enumerating every HSM key (COSMIAN-2026-052)
- Require the `Rekey` permission on the public key named by the Public Key Link of the private key in `ReKeyKeyPair` (`Object_Not_Found` otherwise), so another user's linked public key is no longer retired (COSMIAN-2026-053)
- Resolve the subject and the issuer of `ReCertify` as the requester instead of the certificate owner (COSMIAN-2026-054)
- Use the ID Placeholder (no table scan) for a `Get Attributes` without Unique Identifier, so it no longer selects another user's newest object (COSMIAN-2026-056)
- Make Decrypt by a bare keyset name reject the modes without wrong-key detection (CBC, ECB, CTR, XTS, ChaCha20, FPE and RSA PKCS#1 v1.5) with `Feature_Not_Supported`, including stored parameters; bare HSM keyset decryption defaults to AES-GCM or RSA-OAEP-SHA256 and never falls back to CBC or PKCS#1 v1.5. **Upgrade action:** address the generation explicitly (`name@N`) for these modes (COSMIAN-2026-057)
- Treat retired HSM key generations as `Deactivated` for Encrypt, Sign and MAC (`Wrong_Key_Lifecycle_State`); Decrypt and verification still accept every generation. Protection eligibility uses a live, fail-closed head lookup and label or date writes invalidate cached metadata (COSMIAN-2026-058)
- Apply the configured KMIP algorithm policy to HSM keys addressed by their UID, including keys never enrolled in a keyset (COSMIAN-2026-059)
- Check the `Rekey` permission before the object type in HSM `ReKey` and hide HSM keys from callers without any grant (COSMIAN-2026-060)
- Count an `X-Vault-Token` as configured authentication on every scope (KMIP, `/v1/crypto`, `/tokenize`, MS-DKE, KV, SSH): with `vault_api_enabled = true` and `vault_auth_verifier_url` as the only authentication method, a request without credentials is rejected instead of running as the default user. The SSH endpoints and `/v1/secrets/password` apply the same rule. **Upgrade action:** send `X-Vault-Token` or authenticate another way, for example an mTLS client certificate whose CN is `default_username` for `ckms` provisioning (COSMIAN-2026-061, [#1437](https://github.com/Cosmian/kms/issues/1437), [#864](https://github.com/Cosmian/kms/issues/864))
- Apply the server `key_encryption_key` to every object-creation path: derived keys, split-key shares, joined keys, key pairs generated by `Certify` and KV secret versions are now stored wrapped; wrapping accepts split-key shares and `Get`/`Export` of a share honours `key_wrap_type = NotWrapped`. **Upgrade action:** join or re-split split-key shares before downgrading, because 5.29.0 cannot join shares created by 5.30.0 (COSMIAN-2026-062, [#1437](https://github.com/Cosmian/kms/issues/1437))
- Keep secrets out of trace and debug logs: `Sensitive<T>` redacts the secret-bearing KMIP fields, and the TTLV serializer stack dumps, `#[instrument]` span fields (private-key big-integer limbs), the TTLV deserializer traces and error messages echoing hex input, the symmetric decrypt trace, the Covercrypt AAD logs, the `ckms sym encrypt` DEK trace, the PKCS#12 password traces, the Azure EKM wrap/unwrap request, the Microsoft DKE encrypted data and the PKCS#11 provider no longer print them; `Debug` of `OpaqueObject` and `RNGSeed` prints only the byte length (COSMIAN-2026-063, [#1426](https://github.com/Cosmian/kms/issues/1426), [#1445](https://github.com/Cosmian/kms/issues/1445))
- Return a fixed text as the `message` of a `DOWN` dependency in the public `GET /health`; the error detail (database driver text with host, user or file paths, PKCS#11 return code) goes to the server log as `health check: ...` (COSMIAN-2026-064)
- Upgrade `rusqlite` 0.37 to 0.41 (`libsqlite3-sys` 0.39.1, bundled SQLite 3.54 or later) and replace `tokio-rusqlite` with an in-house async connection wrapper, fixing RUSTSEC-2026-0459 (CVE-2026-119375, uninitialised page-cache memory) (COSMIAN-2026-065)
- Bump `actix-http` 3.20.3 to 3.21.3, fixing RUSTSEC-2026-0552, RUSTSEC-2026-0553 and RUSTSEC-2026-0554 (request framing and keep-alive timeout) (COSMIAN-2026-066)
- Bump `libz-sys` 1.1.31 to 1.1.33, fixing RUSTSEC-2026-0544 (zlib heap buffer overflow in `gzwrite`, MySQL-family backends) (COSMIAN-2026-067)
- Remove the unmaintained `chrono` (RUSTSEC-2026-0543) and `humantime` (RUSTSEC-2026-0542) crates: `time` replaces `chrono`, AWS XKS `SigV4` verification runs on OpenSSL HMAC-SHA256 instead of `scratchstack-aws-signature`, `ckms login oauth` builds its PKCE challenge locally with `KmsRng` and compares the callback `state` in constant time, and the Kubernetes operator parses refresh intervals with a small internal parser (COSMIAN-2026-068)
- Override the Web UI dependency `minimatch` to `^11.0.1`, fixing the denial of service GHSA-g3hv-75wg-m249 (COSMIAN-2026-069)
- Enforce the `WrapKey` usage mask when wrapping with a Certificate: the certificate's own mask or, when it has none, the mask of the public key it links to with `PublicKeyLink` (same owner); a certificate with neither is refused with `is not meant to wrap keys`. **Upgrade action:** in FIPS builds, link a certificate imported without a usage mask to a public key carrying `WrapKey`, or give it a `CryptographicUsageMask` with `WrapKey` (COSMIAN-2026-070, [#1457](https://github.com/Cosmian/kms/issues/1457))
- Make `DeriveKey` require the Create permission (Crypto Officers are unaffected), apply the `kmip.policy_id` request policy to every KMIP request sent by the JOSE and SPIRE transit routes (a SPIRE policy denial is a client error, not HTTP 500), and answer `does not exist or is not accessible` (`Permission_Denied`) for wrap and unwrap with a missing key or any key the caller may not use. **Upgrade action:** grant Create to users that derive keys (COSMIAN-2026-071, [#1492](https://github.com/Cosmian/kms/issues/1492))
- Refuse to start without any authentication method on a non-loopback address unless `insecure_allow_unauthenticated = true` (`--insecure-allow-unauthenticated`, `KMS_INSECURE_ALLOW_UNAUTHENTICATED=true`, development only; Helm `kms.insecureAllowUnauthenticated`). The Docker image, the packaged `kms.toml` and the Helm chart bind `0.0.0.0`. **Upgrade action:** configure an authentication method or set the opt-in (COSMIAN-2026-072, [#1486](https://github.com/Cosmian/kms/issues/1486))
- Reject Auth Verifier bearer tokens of the admin realm (`_`) and, when `auth_verifier_realm` is set, of any other realm; the UI login enforces the same realm (COSMIAN-2026-073)
- Require `email_verified: true` for JWT and UI OIDC logins and identify users of the second and later `jwt_auth_provider` entries as `email#<jwt_issuer_uri>` (the UI OIDC identity too, unless its issuer is the first provider's). **Upgrade action:** write access grants and role lists for those users in that form; IdPs that omit `email_verified`, such as Microsoft Entra ID access tokens, are rejected (COSMIAN-2026-074)
- Reject with 401 any client certificate CN, JWT identity, Auth Verifier or SAML subject or UI session user equal to `default_username` (HTTP scopes and KMIP socket server); only the API token or the non-authenticated mode acts as `default_username`. **Upgrade action:** choose a `default_username` distinct from every real identity and provision with an API token (COSMIAN-2026-075)
- Throttle `POST /ui/login_as` on the KMS side, always on: 10 attempts per minute per client IP (the peer, or the `X-Forwarded-For` client when the peer is in `trusted_proxy_cidrs`) and 5 per minute per username (case-insensitive; a username over 256 bytes gets `400`), answered with `429 Too Many Requests` and `Retry-After` before any credential is relayed; a `429` from the Auth Verifier is relayed as `429` instead of `401` (COSMIAN-2026-076, [#1487](https://github.com/Cosmian/kms/issues/1487))
- Enforce the Web UI session lifetime on the server and make logout revoke the session: the sealed `auth_session` cookie carries a random session id, a session idle for more than 1 hour or older than 24 hours is refused, and `/ui/logout` revokes the session id so a copied cookie stops working. The revocation is stored in the KMS database (`ui_session_revocations` table, or `ui_session_revoked:<sid>` keys with a TTL in Redis-with-Findex), so a logout is honoured by every instance, and a session is refused when the database cannot be read. **Upgrade action:** on multi-region PostgreSQL with Spock, run `SELECT spock.repset_add_table('default', 'ui_session_revocations');` on every node (COSMIAN-2026-077, [#1487](https://github.com/Cosmian/kms/issues/1487))
- Use `ui_session_salt` as the secret input of the Web UI session-key derivation (the public KMS URL only binds the key to the deployment) and reject a salt that is not random. **Upgrade action:** `ui_session_salt` (`--ui-session-salt`, `KMS_SESSION_SALT`) must be at least 32 random bytes as hex (`openssl rand -hex 32`) or base64, and the same on every instance behind a load balancer; a passphrase stops the server at startup with `ui_session_salt must be random`. The new key invalidates Web UI sessions once, and instances of 5.29.0 and 5.30.0 cannot read each other's cookies (COSMIAN-2026-078, [#1487](https://github.com/Cosmian/kms/issues/1487))
- Reject revoked mTLS client certificates: the new `clients_crl_dir` option (`--clients-crl-dir`, `KMS_CLIENTS_CRL_DIR`) points to an OpenSSL hashed directory of CRLs checked on the HTTPS and KMIP socket servers, fail-closed (a missing or expired CRL of the issuing CA rejects its clients). **Upgrade action:** to enforce revocation, set `clients_crl_dir` (requires `clients_ca_cert_file`), run `openssl rehash` and publish renewed CRLs under the next suffix (`.r1`, `.r2`, ...) (COSMIAN-2026-079, [#1493](https://github.com/Cosmian/kms/issues/1493))
- Stop a failing database lookup from looking like "nothing found": `Locate`, CRL generation and OCSP return the error, and OCSP answers an unsigned `tryLater` response instead of `unknown` (COSMIAN-2026-080, [#1493](https://github.com/Cosmian/kms/issues/1493))
- Cap CRL downloads while streaming (chunked responses included), cache only parseable CRLs (256 entries, 64 MiB) and run at most 8 downloads at once (COSMIAN-2026-081, [#1493](https://github.com/Cosmian/kms/issues/1493))
- Resolve CRL Distribution Point host names in the KMS, reject them when any address is internal, then pin the address; the blocked IPv4 ranges include `0.0.0.0/8`, `100.64.0.0/10`, `192.0.0.0/24`, the documentation, benchmarking, multicast and reserved ranges, and IPv6 multicast, documentation and NAT64-embedded addresses. **Upgrade action:** a CRL Distribution Point on a private, CGNAT or other blocked address is no longer fetched (`Validate` reports the chain invalid, `Import` warns and keeps `Active`); publish the CRL on a public address or serve it from the KMS (`kms_public_url`) (COSMIAN-2026-082, [#1493](https://github.com/Cosmian/kms/issues/1493))
- Stop marking an imported certificate `Compromised` when its CRL cannot be fetched, parsed or verified: only a certificate listed in a verified CRL is (COSMIAN-2026-083, [#1493](https://github.com/Cosmian/kms/issues/1493))

### 🚀 Features

#### Multi-node Cluster & Multi-region ([#1366](https://github.com/Cosmian/kms/issues/1366))

- Run scheduled jobs (auto-rotation, CRL refresh, metrics reconciliation, KV secret TTL expiry) under a PostgreSQL advisory lock or a MySQL/MariaDB named lock, so a job runs on one node at a time; SQLite is single-node and Redis-with-Findex is not coordinated yet. When Percona XtraDB Cluster refuses named locks in strict mode, the server logs one warning and runs the jobs on every node, as before
- Write a node heartbeat to the new `cluster_nodes` table (a node is gone after 15 s without heartbeat), elect a leader for display only, and add the authenticated `GET /cluster/status` and the `kms.cluster.nodes` metric
- Report per-dependency latency and HSM status in `GET /health`: a failing HSM is `DEGRADED` (HTTP 200), a failing or silent database is `DOWN` (HTTP 503); each HSM slot and the database are probed with a 2 s limit, so `/health` never hangs. `GET /health?strict=true` answers 503 for `DEGRADED` too (for load balancers and Keepalived), and a `kmip` dependency reports the KMIP socket server task, `DEGRADED` when it has stopped
- Add the Web UI **Server Health** page (`/ui/server-health`) with the status of `GET /health`, each dependency with its latency and message, the live nodes of `GET /cluster/status` and a manual or periodic refresh, plus a three-state footer marker; `GET /health` and `GET /version` answer the origins of `cors_allowed_origins`, the footer fetches `/health` on its own with a 5 s timeout so a slow or non-JSON answer no longer hides the server version, and a `DEGRADED` node is no longer shown in red
- Add the `region_role` setting (`--region-role`, `KMS_REGION_ROLE`, `leader` by default or `follower`) for multi-region active-active deployments on PostgreSQL with logical multi-master replication or MySQL Galera (a follower on SQLite or Redis-with-Findex is rejected at startup): CRL generation and Crypto Officer ceremony activation and revocation run on the leader only (a follower answers HTTP 422), key auto-rotation and renewal warnings run on the leader only, and the KV/SSH internal identifier key is initialised by the leader
- Keep `cluster_nodes` out of the replication set, merge `gcm_invocations.count` by Spock delta-apply so regional counts add up, and make lifecycle events advance the object version so conditional writes reject snapshots taken before a state transition
- Make scheduled jobs mutually exclusive across Galera nodes: when the database refuses `GET_LOCK` (Percona XtraDB Cluster strict mode, MariaDB Galera), a job takes a replicated 300 s lease in the new `kms_cron_leases` table, renewed every 100 s, and another node takes over once it expires; until now every node ran every job. **Upgrade action:** upgrade every node (old and new nodes do not exclude each other until then, so jobs may run twice during a rolling upgrade) and keep the database nodes NTP-synchronised ([#1511](https://github.com/Cosmian/kms/issues/1511), [#1535](https://github.com/Cosmian/kms/pull/1535))
- Make MySQL lifecycle writes monotonic (`Destroyed` and `Compromised` never regress, `Destroyed_Compromised` is kept, a payload update never brings key material back on a `Destroyed` object) on every MySQL deployment, and accept a column or index created by another node between the existence check and the `ALTER`/`CREATE INDEX`, so nodes starting together on a fresh database no longer stop with `Duplicate key name 'idx_objects_owner'`
- Give PostgreSQL `tags` and `read_access` a primary key, add an identity primary key `id` to `crypto_officer_activations`, and create the insert-only `object_state_events` and `object_state_event_tombstones` tables with triggers that derive `objects.state` from them; the log is reconciled with `objects` at every startup. **Upgrade action:** stop every older node before starting the first 5.30.0 node: while the triggers are installed, the state written by 5.29.0 is replaced by the state derived from the events. For a deliberate downgrade, drop the three lifecycle triggers first (see Database tables)
- Start `cosmian_kms configure` with the deployment-profile decision tree of the high-availability guide: the profile restricts the database choice, writes `region_role`, skips the "clear database" prompt for shared data, defaults the HTTP and KMIP socket hosts to `0.0.0.0` for multi-node profiles and prints the operating notes
- Document the [Cluster coordination](documentation/docs/installation/cluster_coordination.md) page, the reworked [High availability and deployment profiles](documentation/docs/installation/high_availability_mode.md) page with the [HAProxy and Keepalived](documentation/docs/installation/haproxy_keepalived.md) setup, `strict` and the `kmip` dependency in OpenAPI, and the Galera and multi-region deployments
- Test with `mise run test:db:multi-region-guards` (pgEdge proofs of CRL and ceremony gating, object-state conflict merge, grant races, primary keys and operator-configuration detectors), wire the pgEdge, Galera and guard legs into CI, and cover the health client, the Server Health page and the footer with unit and Playwright tests

#### Database Migration Runner ([#1270](https://github.com/Cosmian/kms/issues/1270), [#1271](https://github.com/Cosmian/kms/issues/1271), [#1272](https://github.com/Cosmian/kms/issues/1272))

- Add a shared version-sequenced startup migration runner with per-step completion markers and persisted version checkpoints, wired into SQLite (sidecar file lock, retried every 500 ms for up to 31 minutes; resumable wrapping-key ID and certificate serial-tag backfills), PostgreSQL, MySQL, MariaDB and Percona XtraDB Cluster (cross-instance locks), and Redis-with-Findex (30-minute `kms_db_migration_lock` lease and resumption of interrupted runs, with `5.20.0`/`5.24.0`/`5.28.0` fixtures). Databases stamped by a newer KMS, or older than `5.0.0` (SQL) or `5.12.0` (Redis-Findex), are refused at startup
- Add the `StoredStateSync` startup step (SQLite, PostgreSQL, MySQL/MariaDB, Redis-with-Findex): it writes the lifecycle state clients already see (the `objects.state` column) into the stored attributes and key-block attributes, which can lag the column after `Deactivate`, `Destroy` and `Revoke`; rows with a NULL state or attributes are skipped, destroyed objects keep their pinned payload, and unparsable rows are skipped with a warning. API output is unchanged ([#1539](https://github.com/Cosmian/kms/pull/1539))
- Convert PostgreSQL object attributes from `json` to `jsonb` once instead of rebuilding the attribute expression indexes under an exclusive lock at every startup, skip data backfills when `--clear-database` is set, and correct the documented MySQL primary-key schema update version to `5.14.0`
- Test every release from 5.9.0 with `mise run test:db:upgrade`, which replaces `test:upgrade-db`, `test:db:upgrade-all` and `test:db:upgrade-sqlite`: each backend fills a database with a published image, upgrades it to the branch server and re-verifies it after the upgrade, a restart and a restore, with and without a key encryption key; the nightly `db:upgrade` CI leg runs it (schedule, tag and dispatch only). The verifiers accept the two Get Attributes reporting changes of 5.13.0 (`KeyFormatType` in the format a Get returns, `State` from the enforced column) and Redis 5.12.x re-certified certificates whose record lost a tag

#### Vault-compatible API & KV Secret Store ([#863](https://github.com/Cosmian/kms/issues/863), [#864](https://github.com/Cosmian/kms/issues/864), [#1365](https://github.com/Cosmian/kms/issues/1365))

- Add a Vault KV v2-compatible secret store backed by KMIP `SecretData` objects, served on `/<kv_mount>` and `/v1/<kv_mount>` so the `vault` and `bao` CLIs can use the KMS: versioned writes and reads (`?version=N`), soft delete, metadata, `LIST`, hard delete, `options.ttl` with a background sweep that wipes destroyed versions, `options.cas` and `options.expected_owner`. Enable it with the new `[kv]` settings `kv_enabled` (default `false`), `kv_mount` (default `kv`) and `kv_ttl_check_interval_secs` (default `30`, `0` disables the sweep); a `kv_mount` equal to `vault_transit_mount` or `vault_pki_mount` is refused at startup
- Take KV access rights from the path's metadata object (write needs `Import`, read needs `Get`, metadata and listing need `Locate` or `Get`, deletes need `Destroy`), derive its identifier from the path with a server key (`kv_metadata_uid_key`), serialise concurrent writes with a database compare-and-swap (the loser gets `409 Conflict`), enforce TTL expiry per version on read, bound paths to 1,000 versions and 10,000 list candidates, strip user-supplied system (`_`) tags on `Import` and reject them on `Create`, and answer all malformed requests with the Vault `errors` envelope. **Upgrade action:** a UI session-cookie write on the KV scopes must send `Content-Type: application/json` (or `application/octet-stream`), otherwise `415`
- Add KMS-managed short-lived OpenSSH certificate issuance (`/v1/ssh/*`) with roles (`allowed_users`; an empty list restricts a role to Crypto Officers), CA key re-validation at signing time, the Key ID `<requester>/<role>/<serial>`, `SSH_CERTIFICATE_ISSUED` audit events and 3072-bit minimum RSA keys, and password generation (`/v1/secrets/password`); a role user needs no raw `Sign` right on the CA key and HSM CA keys must be created sensitive
- Add HashiCorp Vault auto-unseal with `seal "transit"`: the Transit engine adds `aes256-gcm96` keys (the default type), `encrypt/{name}` and `decrypt/{name}` with `vault:vN:` ciphertexts and `keys/{name}/rotate`, backed by non-exportable AES-256 KMS keys, one per version
- Add `ckms kv put|get|list|delete`, `ckms ssh sign|ca create|ca set|ca public-key|role put`, `ckms password`, and the Web UI pages **Secrets (KV)**, SSH certificate signing, **SSH CA & Roles** and password generation (key pairs are generated in the browser)
- Document the KV store, OpenBao KMIP auto-unseal, the HashiCorp Vault auto-unseal guide, SSH CA setup and a database-agnostic external credential rotation pattern; test against the real OpenBao CLI and a real `sshd` (`test:interop:openbao`, `test:db:openbao`, `test:interop:openbao-kmip`, `test:interop:ssh-secrets`, `test:spire:vault-transit-seal`) and add the `no-committed-credentials` pre-commit hook

#### AES-CMAC & AES-GMAC ([#1367](https://github.com/Cosmian/kms/issues/1367))

- Add AES-CMAC (NIST SP 800-38B) and AES-GMAC (NIST SP 800-38D) to the KMIP `MAC` and `MACVerify` operations, single-part and multi-part, with AES-128/192/256 keys, selected by `Block Cipher Mode` = `CMAC` or `GCM`; a GMAC `MAC Data` is the 12-byte IV followed by the 16-byte tag, GMAC runs through the OpenSSL provider's `GMAC` `EVP_MAC` (FIPS provider included), the vendor extension `IVCounterNonce` lets a client choose the IV (random when absent), and the default KMIP algorithm policy allows `CMAC`
- Add `ckms mac compute|verify --mode {hmac,cmac,gmac}` (the AES key needs the `MAC Generate` and `MAC Verify` usage bits), the `CKM_AES_CMAC` and `CKM_AES_GMAC` PKCS#11 mechanisms, delegation of AES-CMAC and AES-GMAC to HSM-resident AES keys, and a MAC type selector in the Web UI whose type and hash lists come from the WASM client (data and MAC fields must be whole hex bytes)
- Generate every AES-GCM IV inside the OpenSSL FIPS provider in a FIPS build (NIST SP 800-38D §9.1) and reject an `Encrypt` or `MAC` (GMAC) request, a PKCS#11 `C_EncryptInit` or an HSM encryption carrying a client-chosen IV; a FIPS build never sends an IV to an HSM and rejects RSA PKCS#1 v1.5 and SHA-1 OAEP encryption on HSM keys. **Upgrade action:** leave `IVCounterNonce` and `--nonce` out for AES-GCM (the server returns the IV it generated; `C_EncryptMessage` with `CKG_GENERATE_RANDOM` is the PKCS#11 way); the option `allows_caller_iv_in_fips` is removed; non-FIPS builds still accept a caller IV
- Count the AES-GCM invocations of each key in the new `gcm_invocations` table and answer `Encrypt`, `MAC` and AES-GCM wrapping with `Permission_Denied` once a key reaches 2^32 invocations (NIST SP 800-38D §8.3; decryption stays possible, re-key to continue). Invocations are leased from the store in blocks of 4096 per key and node, so the recorded count can exceed the real one by at most 4095 per key and node run; Redis-with-Findex enforces the cap too. **Upgrade action:** a downgrade is degraded, because 5.29.0 does not count its own invocations (see `gcm_invocations` in the database tables documentation)

- Reduce CI cost: add small Nix dev-shell, `build.rs` OpenSSL and Windows vcpkg caches, keep MySQL-family FIPS legs, HSM benchmarks, the full Windows lib suite and publication dry runs in non-PR runs, pin the package upload host key, run the PKCS#11 support report and `pkcs11-check` once in the `pkcs11` group job, stop passing the Google, AWS and Azure test secrets to any job but `test-cloud`, and connect with `hyper-util`'s `HttpConnector` (IPv6/IPv4 happy eyeballs), which avoids a ~2 s wait on Windows when `localhost` resolves to `::1` first
- Reduce Docker Hub pull-rate-limit exposure: authenticate Docker Hub pulls with the `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` secrets (skipped when absent, for example fork PRs) and collapse the `features`/`link` and `features` matrix axes of `packages-test` and `alpine-packages-test` into in-job loops (56 to 14 and 12 to 6 legs, same combinations)
- Run the `ui`, `wasm` and `spire` test types in a `test-nix-js` job that receives no cloud or test secrets, add the `npm-dependency-audit` job (`mise run audit:npm`: npm policy check, OSV-Scanner on `ui/pnpm-lock.yaml`, `npm audit signatures`; on a pull request OSV-Scanner fails only on advisories the base branch does not already have) and install `npm@11.11.0` before it (npm 10.9.9 intermittently stopped `npm audit signatures` with `EMISSINGSIGNATUREKEY`)
- Run `mise run test:docker-scan` after `Test Docker image` in `packaging-docker.yml` (Syft and Grype on the image, `Cargo.lock` and `ui/pnpm-lock.yaml`; fails on fixable High or Critical findings; SBOMs and reports uploaded as `image-scan-*`), and add the `npm` ecosystem for `/ui` to `dependabot.yml`
- Run `mise run docs:check-ai` (AI-docs validator) in the documentation job and the `Benchmark` workflow nightly on `develop` (02:00 UTC) with a `compare` job that runs `mise run bench:compare <version> <ref> 5 --fail` against the highest released version with a published `ckms_bench` report; install Nix before the `bench:hsm` and `bench:pkcs11` steps of `benchmark.yml` and run only `bench:load` when `server_version` is set
- Isolate package signing in `sign-packages`, `sign-apk` and `sign-k8s-plugin` jobs (build jobs hold no GPG key), declare job-level permissions in every workflow, pass workflow inputs through `env:` instead of expanding them in `run:` scripts and make `cargo-deny` deny unknown registries and git sources ([#1500](https://github.com/Cosmian/kms/issues/1500))
- Take the dispatched `packaging.yml` run ID of the nightly `package-and-commit-sbom` job from the URL printed by `gh workflow run` and poll the run list for up to 3 minutes when none is printed, instead of a single query after a fixed 10 s sleep
