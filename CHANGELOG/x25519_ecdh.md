## Breaking Changes

### KMIP (`cosmian_kmip` public API)
- `kmip_2_1::kmip_operations::DeriveKey.object_unique_identifier` changed from a scalar `UniqueIdentifier` to `Vec<UniqueIdentifier>` (the equivalent KMIP 1.4 field, `DeriveKey.unique_identifier`, changed from a scalar `String` to `Vec<String>`), to support asymmetric (two-key) derivation. Any external code constructing `DeriveKey` via struct literal or reading this field as a scalar will need to migrate to `Vec` or to the new `DeriveKey::new_single_base` / `DeriveKey::new_asymmetric` constructors. This is a Rust API break only — the KMIP wire format (TTLV and KMIP-JSON-over-TTLV) is unaffected: a single identifier still serializes/deserializes as exactly one "Unique Identifier" tag, so existing PBKDF2/HKDF requests from unmodified clients remain wire-compatible.

## Features

### KMIP / Crypto
- Add non-FIPS X25519 key agreement support to `DeriveKey`, including repeated base-object identifiers for asymmetric derivation requests.
- Store X25519 shared secrets as non-extractable `SecretData` objects with reciprocal derivation links so clients can chain HKDF and later destroy intermediates.

### Client / WASM
- Add a typed Rust client helper for asymmetric X25519 `DeriveKey` requests and update existing single-base builders to use the new constructors.

## Security

### KMIP / Crypto
- Harden asymmetric `DeriveKey` curve validation to check the OpenSSL key `Id` actually constructed from each referenced object's key material, instead of relying solely on the object's declared curve attribute. This closes an Ed25519/X25519 key-type confusion edge case identified during threat modeling (both curves share a 32-byte raw key length).

## Documentation

### KMIP / Use cases
- Document the X25519 shared-secret to HKDF to `ChaCha20Poly1305` sealing workflow, including 12-byte nonce handling and recommended AAD contents.
