## Security

- Throttle `POST /ui/login_as` (Web UI password login through the Auth Verifier) on the KMS side, always on: 10 attempts per minute per client IP (the peer, or the `X-Forwarded-For` client when the peer is in `trusted_proxy_cidrs`) and 5 per minute per username (case-insensitive; a username over 256 bytes is refused with `400`), answered with `429 Too Many Requests` and `Retry-After` before any credential is relayed. A `429` from the Auth Verifier is now relayed as `429` instead of `401` (COSMIAN-2026-076, [#1487](https://github.com/Cosmian/kms/issues/1487))
- Enforce the Web UI session lifetime on the server and make logout revoke it: the sealed `auth_session` cookie carries a random session id; the server refuses a session idle for more than 1 hour (activity extends it, the cookie is re-issued at most every 5 minutes) or older than 24 hours, and `/ui/logout` revokes the session id so a copied cookie stops working. The revocation is stored in the KMS database (new `ui_session_revocations` table, or `ui_session_revoked:<sid>` keys with a TTL in Redis-with-Findex), so a logout on one instance is honored by all instances behind a load balancer; if the database cannot be read the session is refused. Disabling an account at the identity provider or the Auth Verifier does not end an open session before its expiry. **Existing Web UI sessions are invalidated once at upgrade: users log in again** (this cookie format change comes on top of the cookie replacement of [#1480](https://github.com/Cosmian/kms/issues/1480); one re-login covers both) (COSMIAN-2026-077)
- Use `ui_session_salt` as the secret input of the Web UI session-key derivation (the public KMS URL only binds the key to the deployment) and refuse a salt that is not random. **Setup action**: `ui_session_salt` (`--ui-session-salt`, `KMS_SESSION_SALT`) must now be at least 32 random bytes encoded as hex (`openssl rand -hex 32`) or base64; a passphrase, even a long one, stops the server at startup with `ui_session_salt must be random`. The new key invalidates sessions once; during a rolling upgrade instances running the old and the new version cannot read each other's cookies. Use the same value on all instances behind a load balancer (COSMIAN-2026-078)
- **Setup action** (multi-region PostgreSQL with Spock only): after upgrading, run `SELECT spock.repset_add_table('default', 'ui_session_revocations');` on every node so that a logout is replicated to the other regions

## Bug Fixes

### Hardening

- Harden the HTTP clients that call the Auth Verifier and the Vault-compatible token verifier (UI login, logout, session liveness, `vault_auth_verifier_url`): redirects are never followed and requests time out (5 s connect, 10 s total). **Setup action**: `auth_verifier_url`, `auth_verifier_jwks_uri` and `vault_auth_verifier_url` must use `https://`; `http://` is accepted only for a loopback host (`127.0.0.1`, `::1`, `localhost`), otherwise the server refuses to start (`*_accept_invalid_certs` does not relax this). The response relayed on the unauthenticated `/v1/auth/*` proxy is limited to 1 MiB (`502` beyond) ([#1487](https://github.com/Cosmian/kms/issues/1487))
- Pick up a rotated Auth Verifier signing key without a restart: the JWKS is refreshed periodically, a token that no cached key validates triggers one more fetch (at most every 5 seconds), and a failed fetch keeps the last good keys ([#1487](https://github.com/Cosmian/kms/issues/1487))
